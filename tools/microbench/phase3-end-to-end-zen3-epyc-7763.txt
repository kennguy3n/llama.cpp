Phase 3 end-to-end llama-bench results: Q1_0_g128 4x4 AVX2 repack on Zen 3.
Companion to baseline-zen3-epyc-7763.txt (Phase 2 microbench harness).

Host:
  AMD EPYC 7763 (Zen 3, AVX2 only, no AVX-512), 4 vCPU, 8 GiB RAM
  Linux 6.x, GCC, -DCMAKE_BUILD_TYPE=Release, -DGGML_CPU_REPACK=ON
  llama.cpp commit 8d6c3379 (prism branch + Phase 3 fix for GEMM stride /
  q8_0x4 unpack; supersedes the original 27.03 t/s number which was on
  silently corrupted output - see History section at the bottom).

Model:
  Bonsai-1.7B Q1_0_g128, 248302272 B (231.13 MiB)
  Path: /home/ubuntu/repos/cv-guard/models/slm/Bonsai-1.7B.gguf
  No GGUF format change; runtime repack happens at tensor allocation time.

Methodology:
  llama-bench, default warmup, -r 5 (medians shown as t/s ± stdev)
  A/B: same binary, same model, same flags. Baseline run from a `git stash`
  of the Phase 3 changes; repack run from the working tree with all changes
  applied. Both runs done back-to-back on a quiet VM.

Results (-t 4):

  Variant                         | pp512 (t/s)    | tg64 (t/s)
  --------------------------------|---------------:|-----------:
  Existing single-row AVX2 path   | 22.62 ± 0.04   | n/a (not run)
  Phase 3 4x4 GEMV+GEMM (fixed)   | 25.29 ± 0.17   | 20.56 ± 0.14

  Speedup: 25.29 / 22.62 = 1.118x prefill on validated, bit-identical
  output. The gap from the Phase 2 microbench projection (1.28x) and from
  the original buggy measurement (1.195x) is consistent with the new GEMM
  unpack-from-block_q8_0x4 step that was required to keep the output
  correct (see History below); the prefill graph also doesn't fully
  bottleneck on the q1_0_g128 matmul - attention, RMS norms, ROPE, and
  embedding lookups don't benefit from the kernel change.

Parity:

  tests/test-q1-g128-repack-parity.cpp (synthetic 4 rows x 512 weights):
    Test 1: GEMV (nr=1) - 4 rows, all diff=0.000000e+00 OK
    Test 2: GEMM (nr=4) - 16 elements, all diff=0.000000e+00 OK
    Test 3: GEMM (nr=8) - 32 elements, all diff=0.000000e+00 OK
  All 50 ctest targets pass (-DLLAMA_BUILD_TESTS=ON).

  llama-cli smoke test:
    Prompt: "The capital of France is"
    Output: "The capital of France is **Paris**. It is also..."
    (vs the buggy version which produced `?` characters; see History.)

History:

  The first Phase 3 commit measured 27.03 t/s prefill, but Devin Review
  caught two correctness bugs in the GEMM wrappers in arch/x86/repack.cpp
  and repack.cpp:
    1. The GEMM divided `bs` (already in float-element units, since
       nb0 == sizeof(float) for FP32 outputs) by sizeof(float) a second
       time, so each row's output was written 4x closer than it should
       have been and rows 1..3 silently overwrote row 0.
    2. The GEMM also misread its src1 input - the dispatcher
       (forward_mul_mat_one_chunk + ggml_quantize_mat_q8_0_4x4) packs
       activations as block_q8_0x4 (4 rows interleaved, 4-byte
       granularity), but the GEMM was treating that buffer as a flat
       array of block_q8_0.

  Both bugs were silent: llama-bench reported 27.03 t/s of garbage
  tokens (the throughput counter doesn't validate output), but llama-cli
  produced `?` characters instead of real text. The parity test missed
  it because it only exercised the GEMV path (nr=1).

  The fix (this version):
    - Remove the spurious `bs / sizeof(float)` divide in both GEMMs.
    - Unpack 4 rows out of each block_q8_0x4 group on the fly into a
      contiguous block_q8_0 scratch buffer, then call the existing
      single-row-into-4 GEMV. (Loses some perf vs a real 4x4 GEMM, but
      the output is now bit-identical to the single-row vec_dot.)
    - Extend tests/test-q1-g128-repack-parity.cpp to also exercise
      the GEMM path with nr=4 and nr=8; both pass with diff=0.
    - Validate the fix with llama-cli `"The capital of France is"`
      generating real text.

  Final perf: 1.118x prefill on correct output, vs 1.195x on the
  corrupted output. Honest tradeoff: correctness costs ~7% of the
  measured win until a true 4x4 GEMM kernel is written that consumes
  block_q8_0x4 directly without the unpack.

Dispatcher gate:

  Q1_0_g128 only opts into the runtime repack on hosts where AVX2 is
  available AND AVX-512 is not. AVX-512 hosts retain the existing
  single-row path in arch/x86/quants.c (which uses VNNI-style mask blends
  via mmask32 + dpbusd and is faster than the 4x4 repack). NEON / RISC-V /
  Metal / CUDA / Vulkan paths are untouched - they continue to use the
  single-row vec_dot from quants.c.

Next steps:

  - Optional: 8-row interleave on AVX-512 hosts where the existing
