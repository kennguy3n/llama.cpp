Companion to baseline-zen3-epyc-7763.txt (Phase 2 microbench harness).

  AMD EPYC 7763 (Zen 3, AVX2 only, no AVX-512), 4 vCPU, 8 GiB RAM
  Linux 6.x, GCC, -DCMAKE_BUILD_TYPE=Release, -DGGML_CPU_REPACK=ON
  llama.cpp prism HEAD = 68bef1f5 (PR #12 merged) + this PR's true
  4x4 GEMM kernel (`ggml_gemm_q1_0_g128_4x4_q8_0_avx2_4rows`).

Model:

Methodology:
  llama-bench, default warmup, -r 5 (medians shown as t/s ± stdev).
  Three back-to-back runs of llama-bench on a quiet VM; the median row

Why this is faster than the 4-call GEMV:

  The PR #12 GEMM did 4 sequential calls into the single-row 4x4 GEMV,
  one per activation row. That meant:
    - Each block_q1_0_g128x4 weight was loaded (and its 32-bit qbits
      stripe expanded to a 32-byte +-1 mask) 4x per y-group.
    - The acc[4] FP32 accumulator was re-zeroed and re-flushed 4x per
      y-group (instead of once across all 16 (r_a, r_w) pairs).

  The new kernel
  (`ggml_gemm_q1_0_g128_4x4_q8_0_avx2_4rows` in arch/x86/repack.cpp):
    - Loads each weight block once per y-group; expands each row's
      qbits to a __m256i mask once per sub-block, then re-uses across
      all 4 activation rows (16 blendv per sub-block instead of 16
      mask-expansions per sub-block).
    - Holds 16 __m256 accumulators in registers across the inner loop,
      with sub-block FP32 scaling applied at sub-block close (fmadd).
      Some spilling is expected with 16 ymm + scratch -- the spilled
      accumulators stay hot in L1.
    - Keeps the "unpack 4 rows from block_q8_0x4" step but does it
      ONCE per y-group into a 4-buffer scratch (not 4x per y-group as
      PR #12 did). The unpack itself is a small fraction of total
      time (estimated <0.5%).

History:

  PR #12 first measured 27.03 t/s on silently corrupted output (the
  GEMM divided `bs` by sizeof(float) a second time, AND mis-read
  block_q8_0x4 as flat block_q8_0). The bs+layout fix added an
  on-the-fly unpack-from-q8_0x4 + 4 sequential GEMV calls per
  y-group, dropping prefill to 25.29 t/s on validated output.

  This PR replaces the 4-call GEMV with a single true-4x4 GEMM that
  shares qbits load + expansion across the 4 activation rows. The
  unpack step is preserved (it's negligible) but is now done once
  per y-group instead of 4x. Net: 30.87 t/s on validated output --
  past the original buggy 27.03 number, on bit-identical output.

Dispatcher gate:

  Q1_0_g128 only opts into the runtime repack on hosts where AVX2 is
  available AND AVX-512 is not. AVX-512 hosts retain the existing
  single-row path in arch/x86/quants.c (which uses VNNI-style mask
  blends via mmask32 + dpbusd and is faster than the 4x4 repack).
  NEON / RISC-V / Metal / CUDA / Vulkan paths are untouched -- they
  continue to use the single-row vec_dot from quants.c.

Next steps:

  - AVX-VNNI (Alder Lake P-cores, Zen 4) "Kernel B" variant; deferred
    until a target host is available for measurement (qemu/SDE will not
    give meaningful timings).
  - Optional: 8-row interleave on AVX-512 hosts where the existing
    single-row path is already optimal - low priority, possibly not
    worth the GGUF complexity.
  - Optional: eliminate the unpack entirely by writing a chunk-based
    inner loop that consumes block_q8_0x4 directly. Estimated <1% win
    given the unpack is already <0.5% of total time -- not pursued.
